# ADR-001: Adoção da Arquitetura Hexagonal e Stack Tecnológica Principal

**Data:** 27/03/2026

## Status
Aceito

**Autores:** Equipe HomeoFormula (Arthur, Guilherme, Felipe, Milton)

## Contexto
O projeto Plataforma HomeoFormula visa criar uma Área do Cliente web para uma farmácia de manipulação, que necessita ser integrada a um ERP legado existente. Como a aplicação terá que lidar com regras de negócio complexas (como renovação de pedidos e gerenciamento de perfis familiares) e ao mesmo tempo se comunicar com múltiplos serviços externos (banco de dados PostgreSQL, armazenamento MinIO/S3, APIs de ERP), existe um alto risco de acoplamento entre as regras de negócio e as tecnologias de infraestrutura.
Além disso, precisamos definir as ferramentas e tecnologias que darão suporte tanto ao desenvolvimento da interface com o usuário (Frontend) quanto do lado do servidor (Backend) e persistência. Para garantir que o núcleo da aplicação (domínio) permaneça agnóstico e de fácil manutenção, é necessário adotar um padrão arquitetural sólido em conjunto com a stack escolhida.

## Decisões

### 1. Padrão Arquitetural: Arquitetura Hexagonal (Ports and Adapters)
Decidimos adotar rigorosamente a **Arquitetura Hexagonal (Ports and Adapters)** para o desenvolvimento do backend. 
O sistema será estruturado separando claramente as camadas:
- **Domínio/Core**: Onde residem as regras de negócio e entidades.
- **Portas**: Interfaces que definem como o mundo exterior se comunica com o domínio (Portas de Entrada/Inbound) e como o domínio se comunica com o mundo exterior (Portas de Saída/Outbound).
- **Adaptadores**: Implementações concretas das portas, responsáveis por interagir com bancos de dados, APIs externas e frameworks de interface.

### 2. Backend: NestJS
O framework escolhido para o desenvolvimento do lado do servidor foi o **NestJS** (Node.js/TypeScript). 
- Ele se alinha perfeitamente com a Arquitetura Hexagonal devido ao seu robusto sistema de injeção de dependências e modularidade, o que facilita a implementação de Portas e Adaptadores bem definidos.

### 3. Persistência de Dados e ORM: PostgreSQL e Prisma
- **PostgreSQL** será o banco de dados relacional primário para persistir dados da plataforma (cadastros, subperfis, histórico de renovação, etc.).
- **Prisma** atuará como o ORM do projeto, exercendo o papel de um "Adaptador Secundário" (Outbound). O Prisma será isolado pelas Portas de Repositório do Domínio, garantindo que o núcleo não tenha acoplamento com a sintaxe ou regras do ORM.

### 4. Armazenamento de Arquivos: MinIO (S3-Compatible)
Para o gerenciamento e upload de receitas médicas e anexos orçamentários, utilizaremos o **MinIO**.
- Por ser compatível com a API do Amazon S3, ele nos permite desenvolver e testar o envio de arquivos localmente como um Adaptador Secundário, e facilita uma futura migração para a nuvem da AWS sem necessidade de reescrever o código de envio.

### 5. Frontend: React
A interface web da Área do Cliente será construída utilizando a biblioteca **React**.
- O frontend consumirá as APIs expostas pelos Adaptadores Primários (Inbound) do NestJS, provendo uma experiência de usuário rica, centralizada e 100% autônoma.

### 6. Conteinerização: Docker
A orquestração do banco de dados, storage (MinIO) e da própria aplicação localmente será feita via **Docker** e **Docker Compose**.
- Garante isolamento e reprodutibilidade do ambiente de desenvolvimento entre todos os membros da equipe de graduação, além de simplificar esteiras de CI/CD.

## Consequências

**Positivas:**
- **Desacoplamento e Independência:** A lógica de negócio fica isolada. A troca de uma tecnologia de infraestrutura (como banco de dados ou provedor de nuvem) demandará apenas a criação de um novo adaptador.
- **Ecossistema Unificado:** A adoção de TypeScript ponta a ponta (NestJS + React) permite reuso de conhecimento e compartilhamento de contratos/tipos no futuro.
- **Testabilidade:** A Arquitetura Hexagonal combinada com a injeção de dependências do NestJS facilita a criação de testes unitários rigorosos mockando os adaptadores externos.
- **Pronto para Nuvem (Cloud-Ready):** O uso de MinIO, Docker e PostgreSQL prepara o projeto para uma rápida migração para ambientes em nuvem.

**Negativas:**
- **Curva de Aprendizado:** Exige um maior entendimento de padrões de projeto e ferramentas (como Prisma e Docker) por parte da equipe.
- **Maior Complexidade Inicial:** O setup exige a criação de diversas interfaces (boilerplate) e mapeamento de dependências, exigindo um esforço de desenvolvimento maior no início em comparação a uma arquitetura em camadas tradicional.
